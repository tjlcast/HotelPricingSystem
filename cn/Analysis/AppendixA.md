# **附录A**

下表展示了LLM生成的解决方案与[1]中案例研究记录的解决方案之间的比较。

| 方面 | 案例研究 | LLM生成的解决方案 |
| ----- | ----- | ----- |
| **系统结构** | 设计将系统拆分为命令服务（用于写入）和查询服务（用于读取），遵循命令查询责任分离（CQRS），另外还有一个用于集成的导出服务。这些服务部署在私有云网络中的单个API网关后面。命令和查询组件通过事件总线（Kafka）而不是直接调用进行通信。这导致只有少数核心后端服务（命令、查询、导出）处理所有定价功能。 | 设计采用微服务方法，但分离更加细粒度。除了价格管理（命令）和价格查询（读取）服务外，还有专门的酒店管理、费率管理和认证服务。API网关位于所有这些服务之前。事件总线实现服务间的异步通信。查询服务的存在本质上是CQRS的实现。 |
| **组件** | 设计中的每个微服务都使用标准的Spring分层架构构建。这种将实体映射到控制器/服务的方式确保为每个用例识别出所有必需的模块。重点是功能所需的基本组件，并考虑了安全性和基本日志记录。 | 设计中的每个服务都包含多个专门的组件，除了标准的Spring分层组件外（例如计算引擎、事件存储、带发件箱的事件发布器、断路器）。这种设计更加复杂，并融入了可靠性和性能的模式。 |
| **序列图** | 案例研究展示了有限数量的序列图来说明某些功能和非功能场景 | 架构文档包含了所有功能和质量属性场景的序列图。 |
| **契约** | 在迭代2中，展示了少量容器和组件级别的契约，主要用于说明目的。 | 架构文档包含了不同服务的详细容器级别REST契约。端点在表格中描述，包括方法、描述、请求体和响应。此外，还包含了事件和事件载荷的描述。 |
| **通信风格** | 设计强调异步通信。命令服务将价格更改事件发布到事件总线，查询服务和导出服务订阅这些事件。外部交互通过API网关使用同步REST调用，但内部服务通过事件交换数据。 | 设计采用事件驱动架构进行服务间通信。服务将事件（酒店更新、费率更改、价格更改）发布到集中式事件总线，并在需要时订阅。架构还通过API网关为客户端提供同步API。查询服务支持多种协议：为检索价格提供REST和gRPC API。 |
| **领域建模** | 在迭代2中，为酒店定价上下文定义了显式的领域模型。关键领域实体包括酒店、房型、费率和价格，以及价格计算的业务规则。该领域模型局限于命令端（写模型）。查询服务没有维护自己的对象模型；它只是将价格事件存储在数据库中以便快速检索，导出服务同样没有领域数据（只是传递事件）。因此，案例研究设计将"酒店定价"视为一个领域上下文，在命令微服务中集中建模。 | 设计建模了类似的核心概念（酒店、费率、房型、价格、业务规则等），但在服务间分配了责任。这种设计遵循领域驱动设计方法，将领域模型划分到特定上下文的服务中。 |
| **API管理** | 案例研究采用API网关作为所有客户端（用户或外部系统）的单一入口点。网关将请求转发到适当的后端微服务。每个微服务为其功能暴露RESTful端点。在网关和服务级别执行身份验证和基本授权（与云身份服务集成）。在早期设计中没有提及替代协议或版本控制策略；重点是为每个用例提供必要的REST端点。API安全性（例如令牌验证）和请求验证策略被视为保护这些API的一部分。 | 设计也使用中央API网关，将请求路由到适当的服务并应用横切关注点如身份验证、速率限制和输入验证。每个微服务为其领域定义了一组API（在架构的接口部分记录）。设计明确支持API版本控制和多种协议。特别是，价格查询服务为客户的不同需求提供REST API和gRPC接口。 |
| **安全性** | 用户登录（HPS-1）通过利用公司的基于云的用户身份服务进行单点登录处理。当用户提供凭据时，HPS将验证委托给该身份服务，成功后授予具有适当权限的访问权限。每个API调用都必须进行身份验证（例如，通过该身份服务颁发的令牌）。授权检查被提及为一项要求，但如何处理并未讨论。在迭代1中，安全策略如验证和授权参与者、限制资源访问和加密API数据被确定为关键，并从一开始就进行了规划。 | 设计引入了认证服务作为处理认证关注点的专用微服务。API网关将认证请求委托给该认证服务。认证服务反过来通过OAuth2/OIDC协议与相同的云身份提供商集成以验证凭据和令牌。它可能管理用户会话或JWT令牌，也存储授权数据。设计明确提到使用云身份（CON-2）进行用户管理和单点登录，类似于案例研究方法，但这里将其封装在服务中。 |
| **可扩展性** | 案例研究的CQRS和微服务设计的主要动机是解决可扩展性和性能问题。通过将查询端与命令端分离，系统可以独立于写入扩展读取。在迭代3中，设计明确添加了查询服务的复制和负载均衡以增加价格查询的吞吐量。作为事件存储的Kafka也允许根据需要扩展消费者（多个查询或导出处理器）。这种方法确保了外部系统查询价格的重读负载可以通过仅为查询微服务添加资源来满足。其他可扩展性考虑包括避免共享状态（每个微服务都有自己的数据库）和使用无状态服务以促进水平扩展。 | 架构考虑了每个微服务的独立扩展。例如，如果价格查询激增，价格查询服务可以扩展到多个实例而无需触及其他服务。查询服务中包含的分布式缓存层通过减少数据库负载来支持高读取吞吐量。此外，架构在多个维度上考虑了扩展：它使用CQRS来划分读/写负载，并且可以利用多区域部署来分发负载并减少这些区域用户的延迟。容器化一切并通过Kubernetes编排意味着平台可以根据需求自动扩展服务。 |
| **可部署性** | 案例研究考虑在云提供商上部署所有组件。在迭代1中，决定将所有微服务和事件总线保持在私有网络中，只能通过API网关访问（增强安全性）。到迭代3，定义了更具体的部署策略：使用容器编排服务（可能是托管的Kubernetes）来运行和监控微服务，并建立被动冗余（在第二个可用区/区域的备用部署）以在故障时接管。事件总线（Kafka）是托管的持久服务，无需手动管理消息代理。每个微服务都有自己的数据库（例如，命令的SQL数据库，查询的NoSQL数据库），作为托管的云数据库提供。使用支持流水线的专有基于git的平台满足持续部署（CI/CD）。 | 架构指定了强大的部署和DevOps策略。所有服务都打包为容器并部署在容器编排平台（Kubernetes）上，以确保跨环境的一致性。持续集成/持续部署流水线构建镜像，运行测试，并通过暂存环境推广到生产环境。配置单独管理（基础设施即代码和配置仓库）以实现可重现的、特定于环境的部署。为了高可用性，系统部署在多个区域，具有自动故障转移：如果主区域发生故障，辅助区域的服务和数据库副本将接管，使用全局DNS或负载均衡器路由。设计还利用托管的云服务（用于数据库、身份等）来卸载基础设施管理。 |
| **可测试性** | 选择使用Spring框架及其控制反转来促进模块的单元测试。添加了一个关注点（CRN-7）以确保所有自定义业务逻辑组件都可以进行单元测试。这意味着设计将包括一套服务、控制器等的单元测试，可能还有一些针对事件流的集成测试。然而，案例研究描述没有描述完整的测试环境设置。除了标准单元测试外，没有具体提及测试自动化工具或框架。 | 设计专门构建了用于测试的基础设施。它使用TestContainers通过容器化测试环境来启动临时数据库、Kafka代理和其他依赖项以进行集成测试。有一个契约测试套件，以确保每个服务的API满足其消费者的期望（使用消费者驱动的契约和模式验证）。提供了外部系统的模拟版本，以在不依赖实时系统的情况下测试交互。测试基础设施支持自动配置这些组件，以在CI流水线中运行集成测试。此外，测试数据管理工具在测试之间重置和植入数据库以确保隔离。所有这些都集成到CI/CD流水线中，因此测试在每次构建和部署时运行，并带有报告和故障警报。 |
