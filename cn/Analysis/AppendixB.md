# **附录B**

下表比较了LLM生成的解决方案与在线解决方案[18]的解决方案。

| 领域 | Ticketmaster文章 | LLM生成的解决方案 |
| ----- | ----- | ----- |
| **服务粒度** | 少量粗粒度服务（API网关、事件、搜索、预订、支付） | 细粒度微服务：认证、用户、事件、搜索、库存、订单、支付、票据、交付、通知等 |
| **座位预订策略** | 偏好使用Redis中的TTL分布式锁来防止重复预订 | 在库存数据库中使用乐观锁加上缓存失效和事件溯源 |
| **高峰需求缓解** | 建议使用服务器发送事件进行实时座位更新，并可选择基于WebSocket的虚拟等候室 | 没有明确的实时推送或等候室机制；依赖缓存和通过MQ事件的最终一致性 |
| **搜索同步** | 从PostgreSQL到Elasticsearch的变更数据捕获（CDC）管道，以近乎实时地保持索引新鲜 | 事件服务发布**"EventCreated"**消息；搜索服务消费并索引，事件驱动而非CDC |
| **票据生成与交付** | 超出范围——设计在预订确认后停止。 | 专门的票据服务和交付服务，采用多渠道策略（电子邮件/移动） |
| **安全性与合规性** | 假设Stripe处理支付安全；对更广泛的安全性描述不多。 | 明确的PaymentSecurityManager、加密、网关周围的断路器、通过外部IdP的JWT/OAuth |
| **数据存储** | 单一关系型数据库（PostgreSQL）加上Redis和Elasticsearch。 | 每个服务专用数据库、读取副本、潜在的分片和每个域的审计日志 |
