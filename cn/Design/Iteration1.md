# 酒店价格管理系统 - 迭代1

本文档跟踪酒店价格管理系统架构设计过程第一次迭代的进度，遵循属性驱动设计（ADD）方法论。

## 迭代目标

根据迭代计划，本次迭代的目标是：

**建立整体系统结构和部署模型**

## 需要解决的驱动因素

本次迭代将解决以下驱动因素：

- CRN-1：建立整体初始系统结构
- CON-6：云原生方法
- CON-2：云资源托管和身份服务
- CRN-5：建立持续部署基础设施
- QA-7：可部署性

## ADD过程步骤

### 步骤2：通过选择驱动因素确定迭代目标

本次迭代的目标和驱动因素已在上文定义，重点是使用云原生方法建立整体系统结构。

### 步骤3：选择一个或多个系统元素进行细化

由于这是一个全新开发项目的第一次迭代，需要细化的元素是整个酒店价格管理系统。我们需要定义其高层结构，识别主要组件及其关系。

根据架构文档中的上下文图以及约束条件，特别是CON-6（云原生方法）和CON-2（云资源托管和身份服务），我们需要定义：

1. 整体架构风格（例如，微服务、分层等）
2. 系统的主要功能组件
3. 云环境中的部署模型
4. 与外部系统的集成模式

### 步骤4：选择一个或多个满足所选驱动因素的设计概念

| 选定的设计概念 | 理由 | 被淘汰的替代方案 |
|-------------------------|-----------|------------------------|
| 微服务架构 | - 与云原生原则一致（CON-6）<br>- 实现关注点的清晰分离（CRN-1）<br>- 支持独立部署和扩展<br>- 便于基于业务领域划分服务边界 | - 单体架构：会限制独立部署和扩展<br>- 分层架构：不会在组件之间提供足够的解耦 |
| 基于Kubernetes的容器化部署 | - 提供跨环境的一致性（QA-7）<br>- 实现自动化部署和扩展<br>- 支持云原生托管（CON-6）<br>- 适用于主要云提供商（CON-2） | - 虚拟机部署：资源消耗更多且配置速度较慢<br>- 纯函数即服务：不会为所有组件提供相同级别的控制 |
| 带环境提升的CI/CD管道 | - 实现持续部署（CRN-5）<br>- 支持自动化测试和验证<br>- 确保一致的部署（QA-7）<br>- 使用基础设施即代码实现环境一致性 | - 手动部署：容易出错且耗时<br>- 单环境CI/CD：不会支持适当的测试和验证 |
| API网关模式 | - 为外部系统提供单一入口点<br>- 简化客户端集成<br>- 集中横切关注点<br>- 支持系统的解耦 | - 直接服务到服务通信：会产生紧密耦合并增加复杂性 |
| 事件驱动通信 | - 解耦服务<br>- 支持异步通信<br>- 允许系统演进<br>- 解决业务案例中提到的避免紧密耦合的需求 | - 仅同步通信：会在服务之间产生依赖并限制弹性 |
| 身份即服务（IDaaS） | - 利用云提供商身份服务（CON-2）<br>- 提供安全的身份验证和授权<br>- 减少安全开发工作量<br>- 支持单点登录 | - 自定义身份验证系统：需要更多开发和维护<br>- 委托身份验证：不会充分利用云提供商功能 |
