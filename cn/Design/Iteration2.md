# 酒店价格管理系统 - 迭代2

本文档跟踪酒店价格管理系统架构设计过程第二次迭代的进度，遵循属性驱动设计（ADD）方法论。

## 迭代目标

根据迭代计划，本次迭代的目标是：

**设计核心价格计算和发布功能**

## 需要解决的驱动因素

本次迭代将解决以下驱动因素：

- HPS-2：更改价格（主要用户故事）
- QA-1：性能
- QA-2：可靠性
- CON-5：与现有系统的初始REST API集成

## ADD过程步骤

### 步骤2：通过选择驱动因素确定迭代目标

本次迭代的目标和驱动因素已在上文定义，重点是核心价格计算功能及其可靠性和性能，以及与外部系统的集成。

### 步骤3：选择一个或多个系统元素进行细化

基于迭代1中创建的容器图以及对价格计算和发布功能的关注，本次迭代将细化以下元素：

1. **价格管理服务**：这是负责根据基础费率和业务规则计算价格的核心服务，处理价格更改和模拟，维护价格历史，并发布与价格相关的事件。

2. **费率管理服务**：该服务管理费率类型和业务规则，这些是价格计算过程的重要输入。

3. **事件总线**：该组件处理向其他服务和外部系统发布价格更改，这对可靠性要求至关重要。

4. **API网关**：该组件需要细化以支持与现有系统的REST API集成，特别是渠道管理系统。

5. **价格查询服务**：虽然查询功能将是迭代3的重点，但该服务需要初步细化以确保它能够接收和处理来自价格管理服务的价格更新。

### 步骤4：选择一个或多个满足所选驱动因素的设计概念

| 选定的设计概念 | 理由 | 被淘汰的替代方案 |
|-------------------------|-----------|------------------------|
| 命令查询责任分离（CQRS） | - 将写操作（价格更改）与读操作（价格查询）分离<br>- 优化两种操作的性能（QA-1）<br>- 允许独立扩展写服务和读服务 | - 传统的CRUD方法：不会为写操作和读操作提供相同级别的性能优化 |
| 事件溯源 | - 维护价格更改的完整历史<br>- 提供审计功能<br>- 实现可靠的事件发布（QA-2）<br>- 便于重放事件以进行恢复场景 | - 仅基于状态的持久化：会丢失更改历史并使审计更加困难 |
| 发件箱模式 | - 确保可靠的事件发布（QA-2）<br>- 保证恰好一次的传递语义<br>- 防止数据不一致 | - 直接消息发布：可能导致事件丢失或数据与事件之间的不一致 |
| 断路器模式 | - 防止与外部系统交互时的级联故障<br>- 提高系统弹性（QA-2）<br>- 实现优雅降级 | - 没有容错的直接集成：当外部系统不可用时会导致故障 |
| 缓存旁路模式 | - 提高价格计算的性能（QA-1）<br>- 减少数据库负载<br>- 加速频繁操作 | - 无缓存：会导致冗余计算并增加数据库负载 |
| 异步REST集成 | - 解耦系统与外部系统<br>- 提高可靠性（QA-2）<br>- 满足REST API集成要求（CON-5） | - 同步集成：会产生紧密耦合并影响可靠性 |

### 步骤5：实例化架构元素，绘制视图，分配职责并定义接口

基于选定的设计概念，我们现在将细化步骤3中识别的架构元素，并为每个组件分配特定职责。

#### 价格管理服务组件图

价格管理服务细化为以下组件：

| 实例化决策 | 理由 |
|------------------------|-----------|
| 创建PriceCommandController组件 | 提供用于价格更改操作的REST API端点，包括模拟和实际价格更改 |
| 创建PriceCalculationEngine组件 | 实现核心价格计算逻辑，应用业务规则到基础费率以推导出所有房型和费率的价格 |
| 创建PriceCommandRepository组件 | 以事件溯源的方式存储价格更改命令和状态 |
| 创建PriceEventStore组件 | 维护价格更改的完整历史以进行审计和恢复 |
| 创建带发件箱的EventPublisher组件 | 确保将价格更改事件可靠地发布到事件总线 |
| 创建CircuitBreaker组件 | 防止与渠道管理系统交互时的级联故障 |
| 创建PriceCache组件 | 实现缓存旁路模式以提高频繁价格计算的性能 |
| 创建ChannelManagementAdapter组件 | 处理与渠道管理系统的异步REST集成 |

#### 组件职责

**PriceCommandController**：
- 处理价格更改的HTTP请求
- 验证输入数据
- 将请求路由到适当的处理程序
- 向客户端返回响应

**PriceCalculationEngine**：
- 应用业务规则计算派生价格
- 确保计算在100ms内完成（QA-1）
- 在适当时使用缓存数据以提高性能
- 在应用之前模拟价格更改

**PriceCommandRepository**：
- 存储价格更改命令
- 维护价格的当前状态
- 为命令处理提供事务保证

**PriceEventStore**：
- 存储所有价格更改事件
- 支持事件重放以进行恢复
- 实现审计功能

**带发件箱的EventPublisher**：
- 确保域状态更新和事件发件箱的原子性
- 可靠地将事件传递到事件总线
- 提供恰好一次的传递语义

**CircuitBreaker**：
- 监控对外部系统的调用
- 防止级联故障

**PriceCache**：
- 缓存频繁访问的定价数据
- 提高响应时间以进行价格计算
- 减少数据库负载

**ChannelManagementAdapter**：
- 将内部事件转换为外部REST API调用
- 处理重试和退避策略
- 确保将价格更新可靠地传递到渠道管理系统

#### 接口定义

将定义以下接口以支持上述组件：

1. **PriceCommand API**（REST）
   - `POST /api/prices/simulate` - 模拟价格更改而不应用它们
   - `POST /api/prices/apply` - 应用价格更改并发布它们
   - `GET /api/prices/history/{hotelId}` - 检索酒店价格更改历史

2. **内部事件类型**
   - `PriceChangeRequested` - 表示请求更改价格
   - `PriceChangeSimulated` - 包含价格更改模拟的结果
   - `PriceChangeApplied` - 表示价格更改已成功应用
   - `PriceChangePublished` - 表示价格更改已发布到外部系统

3. **外部集成API**（REST）
   - `POST /api/channels/prices` - 向渠道管理系统发送价格更新

### 步骤6：记录设计决策

本次迭代期间做出了以下关键设计决策：

| 驱动因素 | 决策 | 理由 |
|--------|----------|-----------|
| HPS-2 & QA-1 | 为价格管理实现CQRS模式 | 通过分离命令（价格更改）和查询（价格检索）职责，我们可以独立优化每条路径。价格管理服务将专注于高效处理价格更改，而价格查询服务（将在迭代3中进一步细化）将针对处理高容量查询进行优化。 |
| HPS-2 & QA-2 | 使用事件溯源记录价格更改历史 | 将价格更改存储为事件序列提供完整的审计跟踪，支持恢复场景，并实现向下游系统的可靠事件发布。这对于确保100%的价格更改成功发布至关重要。 |
| QA-1 | 为业务规则和当前价格实现缓存 | 通过缓存频繁访问的数据，特别是来自费率管理服务的业务规则和当前价格，我们可以减少计算时间并确保价格计算在所需的100ms内完成。 |
| QA-2 | 使用发件箱模式进行可靠的事件发布 | 发件箱模式确保域状态更改和事件消息原子性更新，防止系统状态和已发布事件之间的不一致。这有助于满足100%的价格更改成功发布这一可靠性要求。 |
| QA-2 | 为外部系统调用实现断路器 | 断路器模式防止当渠道管理系统不可用时的级联故障，提高系统的整体可靠性。它允许系统在降级模式下继续运行，并在外部系统再次可用时自动恢复。 |
| CON-5 | 使用异步REST与外部系统集成 | 异步REST集成将酒店价格管理系统与外部系统解耦，允许价格更改可靠地发布而无需依赖这些系统的即时可用性。这既满足了REST API集成的要求，也满足了高可靠性的需求。 |
| HPS-2 | 在实际应用之前支持价格更改模拟 | 架构支持在应用价格更改之前进行模拟，允许用户在提交更改之前预览其影响。此功能在HPS-2用户故事描述中明确提及，并通过`/api/prices/simulate`端点实现。 |
