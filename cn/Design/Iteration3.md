# 酒店价格管理系统 - 迭代3

本文档跟踪酒店价格管理系统架构设计过程第三次迭代的进度，遵循属性驱动设计（ADD）方法论。

## 迭代目标

根据迭代计划，本次迭代的目标是：

**设计查询功能和可扩展性**

## 需要解决的驱动因素

本次迭代将解决以下驱动因素：

- HPS-3：查询价格（主要用户故事）
- QA-3：可用性
- QA-4：可扩展性

## ADD过程步骤

### 步骤2：通过选择驱动因素确定迭代目标

本次迭代的目标和驱动因素已在上文定义，重点是系统的查询功能并确保其满足可用性和可扩展性要求。

具体来说，我们需要解决：
- HPS-3：用户和外部系统通过用户界面或查询API查询价格的能力
- QA-3：确保维护窗口外价格查询的99.9%正常运行时间
- QA-4：支持每天至少10万次价格查询，具备处理多达100万次查询的能力，且平均延迟增加不超过20%

### 步骤3：选择一个或多个系统元素进行细化

基于迭代1中创建的容器图以及对查询功能和可扩展性的关注，本次迭代将细化以下元素：

1. **价格查询服务**：该服务在迭代1中初步定义，在迭代2中部分细化以接收价格更新。在本次迭代中，我们将充分开发其查询功能，重点优化高容量并确保高可用性。

2. **API网关**：API网关需要细化以高效路由和负载均衡查询请求，包括来自Web应用程序和外部系统的请求。

3. **Web应用程序**：查询价格的用户界面需要细化，以提供高效且用户友好的价格信息访问。

4. **事件总线**：虽然在之前的迭代中已建立，但事件总线需要进一步细化以确保能够处理需要传播到查询服务的价格更新负载。

5. **基础设施组件**：支持上述服务的底层基础设施需要细化以确保满足可扩展性和可用性要求。

### 步骤4：选择一个或多个满足所选驱动因素的设计概念

| 选定的设计概念 | 理由 | 被淘汰的替代方案 |
|-------------------------|-----------|------------------------|
| 读取模型优化 | - 专门为查询操作定制数据模型<br>- 通过非规范化数据提高查询性能<br>- 支持QA-4所需的高查询量 | - 规范化数据模型：需要连接操作降低查询性能<br>- 与写入模型共享数据库：会在读写操作之间产生争用 |
| 多区域部署 | - 通过地理冗余提供高可用性（QA-3）<br>- 减少地理分布用户的延迟<br>- 实现灾难恢复功能 | - 单区域部署：不会提供足够的可用性保证<br>- 全局数据库：复杂性更高且可能存在一致性问题 |
| 分布式缓存 | - 大幅减少频繁查询的数据库负载<br>- 提高常见查询的响应时间<br>- 水平扩展以处理增加的负载（QA-4） | - 仅本地缓存：不会跨多个实例扩展<br>- 无缓存：会对数据库造成过度负载 |
| 水平扩展 | - 允许添加更多实例以处理增加的负载<br>- 支持可扩展性要求（QA-4）<br>- 支持基于需求的弹性扩展 | - 垂直扩展：更昂贵且有上限<br>- 固定容量：不会适应流量增长 |
| API版本控制 | - 允许API演进而不会破坏现有客户端<br>- 支持长期可维护性<br>- 支持逐步采用API更改 | - 无版本控制：会因集成系统而产生破坏性更改风险<br>- 单独端点：会增加维护负担 |
| 速率限制 | - 保护系统免受过度查询负载<br>- 防止恶意或配置错误客户端的资源耗尽<br>- 确保公平的资源分配 | - 无速率限制：会使系统因单个客户端而过载<br>- 基于IP的阻止：过于粗粒度且可能阻止合法用户 |
| 数据库访问断路器 | - 防止高峰期数据库过载<br>- 提高系统弹性<br>- 实现优雅降级 | - 直接数据库访问：在高负载下会有数据库故障风险<br>- 仅超时策略：不会提供主动保护 |

| 实现跨区域数据复制 | 确保跨区域的数据一致性同时保持性能 |
| 实现分布式缓存服务 | 为价格查询服务的所有实例提供共享缓存层 |

#### 组件职责

**PriceQueryController**：
- 处理价格查询的HTTP请求
- 支持版本化API端点（例如，/api/v1/prices）
- 验证输入参数
- 返回适当格式的响应
- 为大型结果集实现分页

**PriceQueryRepository**：
- 提供优化的读取模型访问
- 为不同的价格查询场景实现高效的查询模式
- 支持复杂的过滤和排序操作
- 使用非规范化的数据结构以提高性能

**DistributedCacheManager**：
- 为价格数据实现缓存旁路模式
- 基于价格更改事件管理缓存失效
- 处理实例间的缓存一致性
- 实现分层缓存策略（内存、分布式缓存）

**QueryCircuitBreaker**：
- 监控数据库健康状况和响应时间
- 数据库过载时打开断路器
- 断路器打开时为查询提供后备机制
- 数据库健康状况改善时管理优雅恢复

**RateLimiter**：
- 强制执行每个客户端的速率限制
- 支持已认证与未认证客户端的不同限制
- 通过标头提供速率限制状态反馈
- 记录和监控速率限制违规

**QueryEventHandler**：
- 订阅来自事件总线的价格更改事件
- 基于价格更改更新读取模型
- 维护写入和读取模型之间的一致性
- 处理恢复场景的事件重放

**RegionalReplicationManager**：
- 协调跨区域的数据复制
- 监控复制延迟和健康状况
- 实现冲突解决策略
- 支持跨区域的故障转移和回退

#### 接口定义

将定义以下接口以支持上述组件：

1. **价格查询API**（REST）
   - `GET /api/v1/prices?hotelId={id}&date={date}&roomTypeId={id}` - 返回特定酒店、日期和房型的价格
   - `GET /api/v1/prices/hotels/{hotelId}/dates/{fromDate}/{toDate}` - 返回日期范围内酒店的价格
   - `GET /api/v1/prices/rates/{rateId}` - 返回跨酒店的特定费率的价格

2. **内部事件处理接口**
   - `PriceChangeEventHandler` - 处理价格更改事件以更新读取模型
   - `CacheInvalidationEventHandler` - 处理触发缓存失效的事件

3. **缓存管理接口**
   - `CacheKey` - 缓存键结构以确保一致性
   - `CacheValue` - 缓存数据结构
   - `CacheControl` - TTL和失效策略设置

4. **指标和监控接口**
   - `QueryMetrics` - 暴露查询性能指标
   - `CacheMetrics` - 暴露缓存命中/未命中率和性能
   - `AvailabilityMetrics` - 暴露正常运行时间和可用性数据

### 步骤6：记录设计决策

本次迭代期间做出了以下关键设计决策：

| 驱动因素 | 决策 | 理由 |
|--------|----------|-----------|
| HPS-3 & QA-4 | 为价格查询实现非规范化的读取模型 | 读取模型专门为价格查询定制，采用非规范化的数据结构，最大限度地减少连接操作的需要。这优化了查询性能以处理每天10万到100万次查询的所需量。该模型包括预聚合数据和针对最常见查询模式优化的索引。 |
| QA-3 | 在多个地理区域部署价格查询服务 | 多区域部署通过消除单点故障和提供地理冗余来确保高可用性（99.9%正常运行时间）。如果一个区域出现故障，流量可以自动路由到健康的区域。这种方法还通过将地理分布的用户路由到最近的可用区域来减少延迟。 |
| QA-4 | 实现分层分布式缓存策略 | 缓存策略使用内存缓存快速访问最频繁查询的数据，由分布式缓存服务（如Redis）支持以在实例间共享缓存数据。这在高峰期大幅减少了数据库负载并提高了常见查询的响应时间，支持可扩展性要求。 |
| QA-3 & QA-4 | 对价格查询服务使用水平自动扩展 | 配置Kubernetes水平Pod自动扩展以根据CPU利用率、内存使用率和请求率自动调整服务实例数量。这允许系统弹性扩展以处理不同的负载，从每天10万次查询的最低要求到100万次查询，确保即使在高峰期也能保持可用性。 |
| HPS-3 | 设计具有综合查询功能的版本化API | 价格查询API从一开始就设计了版本控制（例如，/api/v1/...），以便未来演进而不会破坏现有客户端。API支持广泛的查询参数、分页和过滤，以适应Web应用程序和外部系统的不同查询模式。 |
| QA-3 & QA-4 | 在多个级别实现速率限制 | 速率限制既在API网关级别（全局限制）又在价格查询服务级别（每个客户端限制）应用。这保护系统免受可能导致可用性问题的过度负载，并确保高峰期的公平资源分配。基于客户端认证状态应用不同的速率限制，优先考虑已认证的请求。 |
| QA-3 | 为数据库访问实现断路器 | 断路器通过监控健康状况和响应时间来防止数据库过载，在检测到问题时自动打开断路器。在降级模式下，系统仍可以通过提供缓存或稍微过时的数据来运行，保持可用性，同时数据库恢复。 |
| QA-4 | 设计基于异步事件的读取模型更新 | 读取模型基于来自价格管理服务的事件进行异步更新。这将查询性能与写入操作解耦，并允许读取模型专门针对查询性能进行优化。QueryEventHandler确保写入和读取模型之间的最终一致性。 |
