# 酒店价格管理系统 - ADD迭代6：增强模块化和监控功能

本文档描述了酒店价格管理系统的属性驱动设计（ADD）过程的第六次迭代。本次迭代重点关注增强系统的模块化、监控功能和可测试性，同时确保我们避免技术债务。

## 步骤2：通过选择驱动因素确定迭代目标

根据迭代计划，本次迭代的目标是增强模块化和监控功能。与该目标相关的驱动因素包括：

- **QA-6：可修改性** - 系统中添加了使用不同于REST协议（例如gRPC）的价格查询端点。新端点不需要对系统的核心组件进行修改。
- **QA-8：可监控性** - 系统操作员希望在运行期间测量价格发布的性能和可靠性。系统提供了一种机制，可以根据需要收集100%的这些度量。
- **QA-9：可测试性** - 系统及其元素的100%应支持独立于外部系统的集成测试。
- **CRN-4：避免技术债务** - 系统应该是结构良好、可维护和可扩展的，以避免积累技术债务。

这些驱动因素重点关注使系统更易于维护、可观察和可测试，这对于系统的长期健康和演进至关重要。

## 步骤3：选择一个或多个系统元素进行细化

基于本次迭代的驱动因素，将细化当前架构中的以下元素：

1. **价格查询服务** - 该服务需要增强以支持多种协议（REST和gRPC），同时保持协议特定代码和核心业务逻辑之间的清晰分离。这通过允许添加新协议而无需修改核心组件来解决QA-6（可修改性）。

2. **监控基础设施** - 需要添加新的监控基础设施来收集和分析系统指标，特别关注价格发布的性能和可靠性。这通过提供全面的指标收集和分析功能来解决QA-8（可监控性）。

3. **测试基础设施** - 需要建立测试基础设施以支持所有系统组件独立于外部系统的集成测试。这包括：
   - 外部依赖的模拟服务
   - 测试数据管理
   - 集成测试框架
   这通过启用全面的测试功能来解决QA-9（可测试性）。

4. **API网关** - API网关需要增强以支持不同API协议（REST和gRPC）的协议转换和路由。这通过提供添加新协议的清晰方式来支持QA-6（可修改性）。

5. **服务模板和标准** - 需要建立新的服务模板和标准以确保跨所有服务的一致实现监控、测试和协议支持。这通过促进一致、可维护的代码结构来解决CRN-4（避免技术债务）。

当前架构已包含这些组件的基本版本，但本次迭代将重点关注模块化、监控和测试功能来细化它们。这些细化将确保系统更易于维护、可观察和可测试，同时避免技术债务。

## 步骤4：选择满足所选驱动因素的设计概念

|选定的设计概念|理由|被淘汰的替代方案|
|---|---|---|
|增强分层架构|通过协议无关的服务层扩展现有分层架构，支持多种协议而无需修改核心逻辑。与当前架构一致，同时实现协议灵活性。|六边形架构 - 由于保持与现有架构的一致性以及避免通过不一致的架构模式引入技术债务而被淘汰。|
|OpenTelemetry|支持跨服务一致仪器化的行业标准可观察性。通过实现全面的指标收集和分布式跟踪来支持QA-8。|自定义监控解决方案 - 由于维护开销和缺乏生态系统支持而被淘汰。|
|TestContainers|在容器中使用真实依赖进行集成测试，提供一致的测试环境。通过允许针对实际服务实现进行测试来支持QA-9。|手动测试环境设置 - 由于跨环境的复杂性和不一致性而被淘汰。|
|带gRPC的Protocol Buffers|高效的二进制协议，与gRPC配合使用实现高性能通信。通过提供REST的现代替代方案来支持QA-6。|GraphQL - 由于对当前查询模式来说会增加不必要的复杂性而被淘汰。|
|增强API网关|集中横切关注点如协议转换、监控、安全和断路，而无需服务网格的复杂性。支持QA-6和QA-8，同时避免不必要的复杂性。|服务网格 - 由于系统规模的过度复杂性和操作开销而被淘汰；会引入比收益更多的技术债务。|
|合同测试|通过接口合同确保服务兼容性。通过启用服务的独立测试来支持QA-9。|仅端到端测试 - 由于会使测试更脆弱和缓慢而被淘汰。|
|功能标志|实现新功能的逐步推出和A/B测试。通过允许更安全的更改和回滚来支持CRN-4。|直接部署 - 由于会使更改更有风险且更难控制而被淘汰。|
|结构化日志|提供跨服务的一致、机器可读的日志。通过实现更好的日志分析和关联来支持QA-8。|非结构化日志 - 由于会使日志分析更困难而被淘汰。|
|断路器模式|提高系统弹性并提供监控点。通过实现更好的故障检测和监控来支持QA-8。|直接服务调用 - 由于会使系统弹性降低且更难监控而被淘汰。|
|API版本控制策略|在演进API时实现向后兼容性。通过允许协议更改而不破坏现有客户端来支持QA-6。|破坏性更改 - 由于会中断现有集成而被淘汰。|

## 步骤5：实例化架构元素，绘制视图，分配职责并定义接口

### 5.1 组件实例化决策

|实例化决策|理由|
|---|---|
|使用协议适配器层增强价格查询服务|将协议处理与核心业务逻辑分离，使服务能够支持REST和gRPC而无需复制业务逻辑。保持与现有分层架构的一致性，同时实现协议灵活性。|
|向API网关添加协议转换组件|使API网关能够支持多种协议（REST和gRPC）并执行协议转换，减少各个服务直接处理多种协议的负担。|
|添加带OpenTelemetry收集器的监控服务|集中监控基础设施，以最少侵入现有代码的方式从所有服务收集和分析指标。提供系统性能和可靠性的统一视图。|
|在所有外部服务调用中实现断路器监控|提高系统弹性，同时提供有关外部服务交互的宝贵监控数据，特别是对于价格发布等关键操作。|
|添加用于测试的模拟服务基础设施|创建所有外部依赖的轻量级模拟实现，以支持不依赖实际外部依赖的集成测试。包括渠道管理系统、物业管理系统和用户身份服务的模拟实现。|
|实现功能标志服务|提供跨服务功能标志的集中管理，允许新功能的逐步推出和A/B测试功能，而无需代码更改。支持更轻松的维护和实验。|
|添加带关联ID的结构化日志|通过包含关联ID的结构化日志增强所有服务，以跨多个服务跟踪请求。改善诊断和监控功能。|
|为REST和gRPC接口实现Protocol Buffers|使用Protocol Buffers定义服务合同，可以序列化为JSON（用于REST）和二进制（用于gRPC），确保跨协议的一致API定义。|
|添加合同测试基础设施|实现通过定义合同验证服务兼容性的测试框架，确保服务可以独立演进而不会破坏现有交互。|
|在API网关中实现版本感知的API路由|根据客户端请求将请求路由到适当的API版本，允许服务在不破坏现有客户端的情况下演进其API。|

注意：详细的组件图、序列图和接口定义已添加到Architecture.md文档中。

## 步骤6：记录设计决策

本次迭代的设计决策已记录在Architecture.md文档的第10节（设计决策）中。本次迭代添加的关键设计决策包括：

1. **带协议适配器的增强分层架构** - 用于提供协议灵活性，同时保持与系统其余部分的架构一致性。
2. **用于全面监控的OpenTelemetry** - 实现以支持使用行业标准的可观察性框架的可监控性要求。
3. **用于集成测试的TestContainers** - 实现以通过容器化依赖启用现实的测试，提供一致和隔离的测试环境。
4. **带gRPC的Protocol Buffers** - 实现以通过模式驱动的合同和高性能序列化支持多种协议。
5. **带协议转换的增强API网关** - 用于集中横切关注点并简化后端服务。
6. **合同测试** - 实现以确保服务生产者和消费者之间的API兼容性，帮助避免技术债务。
7. **功能标志** - 用于实现新功能的逐步推出并降低引入更改的风险。
8. **带关联ID的结构化日志** - 实现以改进日志分析和跨服务的可追溯性。
9. **断路器模式** - 用于防止级联故障并提高系统弹性。
10. **API版本控制策略** - 实现以允许API演进而不会破坏现有客户端。

## 步骤7：对当前设计进行分析

此分析评估本次迭代中的设计决策在多大程度上解决了为迭代目标选择的驱动因素。

| 驱动因素 | 分析结果 |
|--------|----------------|
| **QA-6：可修改性** - 支持不同协议 | **已满足** - 带协议适配器的增强分层架构、带gRPC的Protocol Buffers以及带协议转换的API网关共同提供了一个全面的解决方案来支持不同协议。协议无关的服务层允许添加新协议而无需修改核心组件，满足了"新端点不需要对系统的核心组件进行修改"的要求。 |
| **QA-8：可监控性** - 测量性能和可靠性 | **已满足** - OpenTelemetry的实现、带关联ID的结构化日志以及断路器模式提供了全面的监控功能。这些组件能够收集100%所需的性能和可靠性度量，具有端到端跟踪、指标收集和异常检测功能。 |
| **QA-9：可测试性** - 独立于外部系统的集成测试 | **已满足** - TestContainers方法、模拟服务实现和合同测试框架为不依赖实际外部依赖的集成测试提供了强大的解决方案。这些组件能够使系统的100%独立于外部系统进行测试，满足要求。 |
| **CRN-4：避免技术债务** - 结构良好、可维护和可扩展的系统 | **已满足** - 多个设计决策有助于避免技术债务：合同测试防止API兼容性问题，功能标志实现更安全的功能部署，API版本控制策略允许API演进而不会产生破坏性更改，增强分层架构保持与现有系统的一致性。这些决策共同确保系统保持可维护和可扩展。 |

架构现在对协议灵活性、监控功能和可测试性有了全面支持，同时保持架构一致性并避免技术债务。本次迭代的所有驱动因素都已通过所做的设计决策得到满足。

本次迭代的设计决策已集成到整体架构中，Architecture.md文档中记录了详细的组件设计、接口定义和实现方法。所选择的方法在当前需求与未来可扩展性之间取得平衡，确保系统能够演进以满足不断变化的需求，同时保持连贯的架构。
